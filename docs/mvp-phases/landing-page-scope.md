# 랜딩페이지 구조 스코프

## Summary

KJV 리더노트의 첫 페이지를 공개 랜딩 페이지로 운영한다. 랜딩의 메시지는 단순 기능 소개가 아니라 "읽던 자리, 마음에 남은 구절, 통독 흐름이 흩어지지 않는 개인 성경 공부 공간"이라는 제품 약속을 중심에 둔다.

랜딩은 방문자가 "이 앱은 성경 읽기 앱이 아니라 내 통독과 구절 기록을 이어주는 도구"라고 느끼게 해야 한다. 기능명은 보조 정보로 두고, 첫 화면에서는 사용자가 이미 겪는 문제와 앱이 주는 변화가 먼저 보여야 한다.

현재 `/`는 공개 랜딩이고 `/app`는 실제 앱 진입점이다. 성경 리더는 로그인 없이 열 수 있게 두고, 계정은 읽기 위치와 기록을 계정 기준으로 이어가거나 서버에 번역 의견을 제출할 때 사용한다.

확인일: 2026-07-15

## Goals

- 비로그인 사용자가 앱의 목적과 사용 이유를 5초 안에 이해하게 한다.
- 첫 화면에서 "내 성경 통독과 구절 기록을 잃어버리지 않는 개인 공부 공간"이라는 정체성을 명확히 보여준다.
- 기능 목록보다 사용자의 실제 고민을 먼저 건드린다.
- 로그인하면 사용자별 기록을 구분하고 개인 노트와 번역 의견 같은 인증 기능을 사용할 수 있다는 점을 설명한다.
- 로그인과 계정 만들기 CTA를 "기록을 이어가기 위한 다음 행동"으로 배치한다.
- 실제 앱 UI preview를 사용해 기능을 과장 없이 보여준다.
- 첫 화면에서 4개의 실제 사용 장면이 영상처럼 전환되는 데모로 제품의 흐름을 체감하게 한다.
- 에메랄드·샴페인·중성색에 한정한 그라데이션과 명확한 명암 계층으로 현대적이고 고급스러운 인상을 만든다.
- Google Play 출시 전에는 Android 앱 출시 예정 상태를 날짜나 다운로드 링크 없이 정확하게 안내한다.
- 추후 Supabase Auth, DB repository, RLS 전환과 충돌하지 않는 route 구조를 잡는다.

## Non-goals

- Google, GitHub, Apple 등 외부 OAuth provider SSO 구현
- 가격 정책, 결제, 구독 플랜
- 커뮤니티, 공유 피드, 공개 프로필
- 고품질 AI 음성, 오프라인 모드, 구절 이미지 생성
- 성경전서 전체 본문 라이선스 확정 전 전체 본문 홍보
- 실제 개인 데이터 DB 동기화가 완료되지 않은 상태에서 "모든 기기 동기화"라고 표현하는 것
- Play Console 공개 전 출시일, 다운로드 링크, 즉시 설치 가능 상태를 확정적으로 표현하는 것

| 이동 중 듣고 싶은 사용자 | "눈으로 읽기 어려운 시간에도 장과 구절을 이어 들을 수 있습니다." |

### Copy Principles

- 기능을 먼저 말하지 말고, 사용자가 얻는 변화부터 말한다.
- "저장", "동기화", "RLS" 같은 기술어는 랜딩 본문에서는 뒤로 보낸다.
- "성경 공부를 더 잘하세요"처럼 추상적인 문구보다 "읽던 자리", "마음에 남은 구절", "다시 꺼내 쓸 구절"처럼 손에 잡히는 표현을 쓴다.
- 보안과 인증은 PR 문구로 과장하지 않고, "내 기록을 내 계정 기준으로 분리"하는 설명으로 둔다.
- 전체 본문, 다기기 동기화, 외부 SSO는 구현 완료 전까지 약속처럼 쓰지 않는다.

| 항목 | 현재 상태 | 랜딩 반영 원칙 |
| --- | --- | --- |
| 앱 이름 | `KJV 리더노트` | H1과 nav brand에 그대로 사용 |

| 개인 데이터 | 주요 읽기 기록은 사용자 ID별 localStorage, 개인 노트·번역 의견 등 일부 기능은 서버 저장 | 저장 위치를 구분하고 "모든 기기 자동 동기화"는 말하지 않음 |
| 성경 본문 | 공개 KJV/fixture/DB 전환 경계가 있음 | 전체 본문 제공 범위는 라이선스 게이트 이후 확정 |

## Target Route IA

| Route | 접근 | 역할 |
| --- | --- | --- |
| `/` | 공개 | 랜딩 페이지 |
| `/app` | 공개, 로그인 권장 | 실제 KJV 리더노트 앱. 비로그인 사용자는 guest localStorage로 읽는다. |
| `/auth/login` | 공개 | 이메일 로그인 |
| `/auth/sign-up` | 공개 | 계정 만들기 |
| `/auth/reset-password` | 공개 | 비밀번호 재설정 |
| `/auth/update-password` | 세션 필요 | 새 비밀번호 저장 |

### Route Behavior

- 비로그인 사용자가 `/`에 오면 랜딩을 본다.
- 비로그인 사용자가 `/app`에 오면 guest 리더로 바로 진입한다.
- 로그인 사용자가 `/`에 오면 랜딩을 그대로 볼 수 있되, CTA는 `내 리더노트 열기`로 바뀐다.
- 로그인 사용자가 `/auth/login` 또는 `/auth/sign-up`에 오면 `/app`으로 이동한다.
- 로그인 후 기본 redirect는 `/app`으로 둔다.

## Section Details

### Top Nav

- 첫 화면에서 `KJV 리더노트` 브랜드를 노출한다.
- 비로그인 상태에서는 `/auth/login` 로그인 링크와 `/app` 바로 읽기 CTA를 함께 제공한다.
- 모바일에서는 공간을 위해 앱 진입 CTA를 숨길 수 있지만 로그인 링크는 유지한다.
- 로그인 상태에서는 중복 보조 CTA 없이 `내 리더노트 열기`만 제공한다.

### Product Preview

- Hero 오른쪽에 실제 앱의 홈·리더·인용 보관·듣기 화면을 기반으로 만든 4장면 정적 UI 데모를 둔다.
- 장면은 `이어 읽기 → 표시와 기록 → 인용 보관 → 말씀 듣기` 순서로 5.2초마다 전환한다.
- 사용자는 장면 선택 버튼과 재생/일시정지 버튼으로 흐름을 직접 제어할 수 있다.
- 데모에 마우스를 올리거나 키보드 포커스가 들어오면, 페이지가 숨겨지거나 데모가 화면 밖으로 나가면 자동 전환을 멈춘다.
- 운영체제의 모션 감소 설정이 켜져 있으면 자동 전환을 비활성화하고 수동 장면 선택만 제공한다.
- 장면 전환은 고정된 stage 안에서 opacity와 transform만 바꿔 레이아웃 이동을 만들지 않는다.
- 데모는 실제 세션이나 localStorage를 읽지 않으며, 구현되지 않은 기능을 보여주지 않는다.
- 데모 안의 장 이름은 문서 outline을 오염시키지 않도록 구조 heading이 아닌 텍스트로 렌더링한다.

### Account And Data Boundary

| 구분 | 사용자에게 보여줄 내용 |
| --- | --- |
| 로그인 없이 | 성경 읽기, 기본 듣기, 이어 읽기, 하이라이트와 인용 보관을 사용하고 주요 기록을 현재 브라우저에 저장한다. |
| 계정으로 | 사용자별 기록 구분, 개인 노트와 번역 의견 같은 인증 기능, 같은 브라우저의 게스트 기록 가져오기를 사용한다. |
| 현재 한계 | 브라우저 데이터를 삭제하거나 다른 기기를 사용하면 주요 읽기 기록이 자동으로 이어지지 않는다. |

- `모든 기기에서 자동 동기화됩니다.`
- `절대 유실되지 않습니다.`
- `Google로 계속하기` 등 아직 구현하지 않은 외부 OAuth 문구

### Final CTA

```txt
오늘 마음에 남은 말씀을 다음 공부까지 가져가세요.

읽던 위치, 표시한 구절, 다시 쓸 인용을 내 리더노트에 정리하고 바로 이어 읽으세요.
```

## Copy Guardrails

- `붙잡은 구절` 대신 `마음에 남은 구절`, `표시한 구절`, `다시 보고 싶은 말씀`처럼 자연스러운 표현을 사용한다.
- 기능명보다 사용자가 얻는 결과를 먼저 말한다.
- `동기화`, `서버 저장`, `보안`은 현재 구현 범위를 구분해 설명한다.
- Android 앱 공개 전에는 `출시 예정` 상태만 알린다.
## Visual Design Direction

- 랜딩은 문서형 SaaS가 아니라 실제 공부 도구를 편집 화보처럼 보여주는 `editorial gradient + app cinema` 방향으로 설계한다.
- 색상 예산은 에메랄드, 샴페인, 아이보리·차콜 중성색으로 제한한다. 배경은 이 색의 방사형·선형 그라데이션을 겹치되 본문 대비를 해치지 않는다.
- Header는 얇은 선과 blur를 사용한 sticky glass surface, Hero는 큰 균형형 제목과 어두운 데모 shell로 명암을 분리한다.
- Hero에는 앱 이름, 제품 약속, CTA, Google Play 출시 예정 안내와 실제 앱 데모가 함께 보이게 한다.
- 핵심 이점은 동일한 카드 3개가 아니라 크기와 명암이 다른 bento 구조로, 계정 경계와 final CTA는 페이지 폭 안에 들어오는 inset panel로 표현한다.
- 큰 장식 카드보다 실제 앱 UI와 기능 밀도를 우선하며, 각 섹션은 짧은 제목·한 문장 설명·실제 UI 단서 중심으로 둔다.
- 모바일에서는 CTA와 데모가 겹치지 않게 하고, 데모 stage 높이를 고정한 채 정보 밀도만 줄인다.
- 랜딩 전용 스타일은 `.landing-page`와 `.landing-demo-*` 범위에 격리해 `/app`의 reader·panel 전역 계약을 바꾸지 않는다.

## Implementation Phases

### L-01: Route Split

작업:

- [ ] 현재 `apps/web/src/app/page.tsx`의 보호 앱 렌더링을 `/app` 경로로 이동한다.
- [ ] `/`는 공개 랜딩 페이지로 바꾼다.
- [ ] `/app`에서 Supabase user가 없으면 guest 리더를 렌더링한다.
- [ ] 로그인 성공 redirect 기본값을 `/app`으로 정리한다.

수용 기준:

- [ ] 비로그인 사용자가 `/`에서 랜딩을 볼 수 있다.
- [ ] 비로그인 사용자가 `/app`에 접근하면 성경 리더를 바로 사용할 수 있다.
- [ ] 로그인 사용자는 `/app`에서 기존 앱을 그대로 사용할 수 있다.

### L-02: Landing Content Components

작업:

- [ ] 랜딩 전용 component 또는 route component를 만든다.
- [ ] Hero와 4장면 데모, proof moments, 계정·데이터 경계, 이점 3개, 3단계 흐름, FAQ, final CTA 섹션을 구현한다.
- [ ] CTA 링크를 `/auth/login`, `/auth/sign-up`, `/app`으로 연결한다.
- [ ] 로그인 상태에 따라 CTA 문구를 바꿀지 결정한다.

수용 기준:

- [ ] 첫 viewport에서 앱 이름, 제품 약속, 로그인 CTA, 제품 preview가 보인다.
- [ ] 데모의 4장면이 자동 전환되고, 장면 선택과 재생/일시정지 제어가 동작한다.
- [ ] hover, focus, page hidden, viewport 이탈, reduced motion 조건에서 자동 전환이 멈춘다.
- [ ] 장면 전환 전후 데모 높이가 변하지 않는다.
- [ ] Hero copy가 기능 나열이 아니라 사용자 문제와 제품 변화를 말한다.
- [ ] 랜딩에 현재 구현되지 않은 OAuth provider나 동기화 약속이 없다.
- [ ] Google Play 공개 전에는 Android 앱을 `출시 예정`으로 안내하고 즉시 설치 가능한 것처럼 표현하지 않는다.
- [ ] preview 내부 장 이름이 구조 heading으로 노출되지 않는다.
- [ ] 모든 CTA가 올바른 route로 이동한다.

### L-03: Responsive And Accessibility

작업:

- [ ] 모바일 390px 폭에서 hero, CTA, preview가 겹치지 않게 한다.
- [ ] desktop 1440px 폭에서 preview가 과도하게 늘어나지 않게 한다.
- [ ] CTA 버튼에 명확한 accessible name을 둔다.
- [ ] 섹션 heading hierarchy를 `h1`, `h2`, `h3` 순서로 유지한다.

수용 기준:

- [ ] 모바일과 데스크톱에서 텍스트가 버튼 또는 preview 위에 겹치지 않는다.
- [ ] 키보드 탭 순서가 nav, CTA, 섹션 링크 순서로 자연스럽다.
- [ ] 컬러 대비가 본문과 CTA에서 충분하다.
- [ ] 모션 감소 환경에서도 모든 장면을 수동 선택할 수 있다.

### L-04: Verification

작업:

- [ ] `npm run lint`
- [ ] `npm run build`
- [ ] 브라우저에서 `/`, `/app`, `/auth/login`, `/auth/sign-up` 흐름 확인
- [ ] 모바일 viewport screenshot 확인
- [ ] 로그인 상태와 비로그인 상태 CTA 확인

수용 기준:

- [ ] `/`는 공개 접근 가능하다.
- [ ] `/app`의 성경 리더는 공개되고, 서버 저장/계정 데이터 기능은 로그인 상태를 요구한다.
- [ ] 로그인 후 기존 리더, 통독, 강조, 인용, TTS 흐름이 깨지지 않는다.
- [ ] 랜딩 카피가 현재 구현 범위를 과장하지 않는다.

## Acceptance Criteria

- [ ] 랜딩 첫 화면에 `KJV 리더노트`가 주요 신호로 보인다.
- [ ] 랜딩 첫 화면이 "읽던 자리, 마음에 남은 구절, 통독 흐름을 이어주는 도구"로 읽힌다.
- [ ] 사용자가 앱의 핵심 이점을 로그인 전에 이해할 수 있다.
- [ ] 카피가 기능 나열에 그치지 않고 사용자 문제와 제품 변화를 말한다.
- [ ] 계정 필요성이 "개인 공부 기록을 계정 기준으로 이어가기 위해서"로 설명된다.
- [ ] SSO/인증 구조는 현재 구현과 맞게 Supabase 이메일 로그인 중심으로 설명된다.
- [ ] 외부 OAuth provider, 다기기 동기화, 전체 본문 제공을 완료 기능처럼 표현하지 않는다.
- [ ] `/`와 `/app`는 공개 접근 가능하되, 개인 계정/서버 데이터 경계가 로그인 상태로 분리된다.
- [ ] `header`, `main`, `footer`가 형제 landmark로 렌더링되고 preview 제목이 heading outline을 오염시키지 않는다.
- [ ] FAQ가 기본 닫힘 상태의 native `details`/`summary`로 제공된다.
- [ ] 로그인 후 기존 앱 기능이 회귀하지 않는다.
- [ ] 모바일과 데스크톱에서 시각적으로 검증된 screenshot을 남긴다.
- [ ] 4개의 데모 장면이 하나의 고정 stage 안에서 영상처럼 전환된다.
- [ ] 자동 전환, 수동 장면 선택, 일시정지와 모션 감소 설정이 모두 동작한다.
- [ ] 데모 장면 전환 중 CLS나 가로 overflow가 발생하지 않는다.

## Open Decisions

- 외부 provider SSO를 실제로 넣을지, 이메일 로그인만 유지할지 결정해야 한다.
- 로그인한 사용자가 `/` 방문 시 자동으로 `/app`으로 보낼지, 랜딩을 보여주고 CTA만 바꿀지 결정해야 한다. 권장은 랜딩 유지 후 CTA 변경이다.
- preview는 실제 앱의 표현 컴포넌트를 일부 재사용하되 세션과 저장소를 읽지 않는 랜딩 전용 static scene으로 확정한다.
- 로컬 데이터 가져오기 안내를 랜딩에서 언급할지, 로그인 후 앱 내부 안내로만 둘지 결정해야 한다. 권장은 앱 내부 안내다.
